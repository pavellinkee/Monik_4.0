# MONIK — РУКОВОДСТВО ПО ЗАПУСКУ

> Техническая документация по эксплуатации. Архитектурные документы в
> `docs/architecture/` этим файлом **не изменяются** (`CLAUDE.md` §43).

## 1. Требования

- Python 3.12;
- [`uv`](https://docs.astral.sh/uv/) для установки зависимостей;
- доступ к API агрегаторов и Telegram Bot API (для production-запуска).

```bash
uv sync --group dev
```

---

## 2. Конфигурация

Конфигурация задаётся YAML-файлом; шаблон — `config/config.example.yaml`.

```bash
cp config/config.example.yaml config/config.yaml
```

Приоритет источников: переменная окружения `MONIK__SECTION__FIELD` >
значение из файла > безопасный default.

### Секреты

Секреты **никогда** не хранятся в файле конфигурации: указывается только
ссылка на переменную окружения.

```yaml
providers:
  - provider_id: oneinch
    api_key: { env: "MONIK_ONEINCH_API_KEY" }
```

Полный список переменных — в `.env.example`. Значения задаются в окружении
процесса, а не в репозитории (`CLAUDE.md` §49).

### Проверка конфигурации

```bash
uv run monik --config config/config.yaml --check-config
```

Команда валидирует конфигурацию, разрешает секрет-ссылки и завершается,
не запуская воркеры. Код возврата `1` означает, что конфигурация
некорректна: значения «по умолчанию» вместо неё не подставляются.

## 3. Первый запуск

```bash
uv run python scripts/init_db.py --config config/config.yaml
uv run monik --config config/config.yaml
```

Порядок запуска приложения фиксирован (`CLAUDE.md` §30):

1. загрузка конфигурации;
2. открытие SQLite;
3. проверка целостности;
4. применение migrations;
5. восстановление незавершённого состояния;
6. инициализация адаптеров;
7. Resource Manager;
8. Scheduler;
9. Telegram;
10. запуск воркеров.

Коды возврата: `0` — штатная остановка, `1` — ошибка конфигурации или
запуска, `2` — остановка в состоянии `SAFE_STOP`, `3` — остановка по
команде «Перезапустить» из Telegram.

Проверить версию можно без запуска:

```bash
uv run monik --version
```

### Окружение

Значение `application.environment` попадает в логи, `/status` и все
уведомления. По умолчанию — `development`, поэтому **боевой запуск обязан
задать его явно**, иначе production будет представляться как development:

```yaml
application:
  environment: production
```

либо переменной окружения (имеет приоритет над файлом):

```ini
[Service]
Environment=MONIK__APPLICATION__ENVIRONMENT=production
```

Если окружение осталось `development`, приложение пишет об этом
предупреждение при старте.

### Служба systemd и переход между версиями

Состояния Monik живут отдельными каталогами рядом друг с другом, а служба
указывает не на конкретный из них, а на символическую ссылку `current`:

```
/home/ubuntu/claude_monik/
├── monik_3.4/          старые состояния
├── monik_3.5/          версия отката
├── monik_4.0/          текущее
└── current -> monik_4.0
```

Действующий юнит хранится в репозитории как `docs/monik.service` — копия
того, что установлено в `/etc/systemd/system/`. Благодаря ссылке он не
содержит номера версии и **не редактируется при обновлении**. Переход на новое состояние — перенос ссылки и перезапуск:

```bash
ln -sfn monik_4.0 /home/ubuntu/claude_monik/current
sudo systemctl restart monik
```

Откат — та же команда с именем прежнего состояния. Версию приложение
определяет по имени каталога, на который ведёт ссылка, и сообщает её в
логах, `/status` и уведомлениях, поэтому по сообщению всегда видно, что
именно работает.

Перед переносом ссылки у нового состояния должно быть готово собственное
окружение:

```bash
cd /home/ubuntu/claude_monik/monik_4.0 && make install
```

**База данных живёт вне состояний** — в `/var/lib/monik/monik.db`. Она
одна на все версии, поэтому накопленная история сканов и возможностей
переезжает вместе с переходом на новое состояние и сохраняется при
откате.

Плата за это — миграции. Новая версия применяет свои миграции к общей
базе, и откат на прежнее состояние получает базу уже новой схемы.
Прежний код обычно её читает — миграции только добавляют колонки, — но
перед переходом на состояние с миграциями базу следует скопировать:

```bash
sudo cp /var/lib/monik/monik.db /var/lib/monik/monik.db.before-<версия>
```

**Проверка перед переносом ссылки.** Конфигурацию нового состояния можно
проверить, не останавливая работающую службу:

```bash
sudo -u ubuntu /home/ubuntu/claude_monik/monik_4.0/.venv/bin/monik \
  --config /home/ubuntu/claude_monik/monik_4.0/config/config.yaml --check-config
```

Секреты служба получает от systemd: `EnvironmentFile=/etc/monik/monik.env`
читается от имени root, а процесс работает от `ubuntu`. Файл остаётся
доступным только root, и права не ослабляются. При ручном запуске
приложение ищет файл само — по порядку `--env-file`, `MONIK_ENV_FILE`,
`/etc/monik/monik.env`, `~/.config/monik/monik.env`, `./.env`.

### Автоматический перезапуск

Команда «Перезапустить» из Telegram корректно завершает работу и выходит
с кодом `3`. Поднимает процесс обратно **менеджер служб**, поэтому unit
обязан быть настроен так:

```ini
[Service]
Restart=always
```

Без этой настройки команда просто остановит Monik.

Перезапуск обязан быть ограничен (`24_DEPLOYMENT.md` §27-28): приложение,
падающее из-за неисправной конфигурации, иначе поднимается бесконечно.
Ограничение задаётся в секции `[Unit]`:

```ini
[Unit]
StartLimitIntervalSec=300
StartLimitBurst=5
```

Пять неудачных стартов за пять минут — и служба остаётся в состоянии
`failed`, а причина видна в `journalctl -u monik`. Временный сбой сети
по-прежнему приводит к нормальному подъёму.

## 4. Остановка

`SIGINT` и `SIGTERM` инициируют graceful shutdown: новые циклы не
создаются, активные задачи получают отмену, состояние сохраняется. Таймаут
задаётся `application.shutdown_timeout_seconds`.

## 5. Резервное копирование

### По расписанию

Копия создаётся автоматически. По умолчанию — **суббота, 03:00**:

```yaml
database:
  backup_enabled: true
  backup_directory: "data/backups"
  backup_retention_copies: 8

scheduler:
  tasks:
    backup:
      mode: weekly
      weekday: 6            # ISO: 1 — понедельник, 6 — суббота
      time: "03:00"
      timezone: "Europe/Lisbon"
```

Копируется **только база SQLite**: она является source of truth
восстановимого состояния (`CLAUDE.md` §28). Виртуальное окружение,
репозиторий, кэши, логи, временные файлы и секреты в копию не попадают.

Копия снимается запросом `VACUUM INTO`, поэтому она согласована даже при
работающем приложении, и сразу проверяется `PRAGMA integrity_check`:
копия, которую нельзя открыть, не засчитывается и удаляется.

Копий сверх `backup_retention_copies` удаляются автоматически — место не
заполняется бесконечно. Ручные и плановые копии называются одинаково и
лежат в одном каталоге, поэтому попадают под общую ротацию.

Сбой копирования не останавливает сканер: задача имеет самый низкий
приоритет. Итог виден в логе и в Telegram по команде `/backup`.

### Вручную

```bash
uv run python scripts/backup_db.py  --config config/config.yaml --output backups/
uv run python scripts/restore_db.py --config config/config.yaml --backup backups/monik-<ts>.db
```

Восстановление не перезаписывает существующую базу без `--force`.

## 8. Telegram

Уведомления и команды включаются секцией `notifications`:

```yaml
notifications:
  enabled: true
  telegram:
    enabled: true
    bot_token: { env: "MONIK_TELEGRAM_BOT_TOKEN" }
    chat_id: { env: "MONIK_TELEGRAM_CHAT_ID" }
    commands_enabled: true
```

Управление и полный список команд описаны в
[`docs/telegram_commands.md`](telegram_commands.md). Кратко: `/menu`
открывает кнопки, `/help` перечисляет команды, `/status` показывает
состояние, `/providers` — состояние агрегаторов и их очередей,
`/start`, `/stop` и `/restart` управляют сканером, `/update` ставит
обновления системы и перезапускает приложение (последние три — с
подтверждением).

Каждое уведомление о возможности содержит кнопку `об`; её текст готовится
заранее, поэтому нажатие не выполняет новых запросов к провайдерам.

## 9. Эксплуатационные заметки

- Уровень логирования задаётся `logging.level`; вывод — структурированный
  JSON с редакцией секретов;
- `/status` показывает состояние подсистем и провайдеров, `/stats` —
  накопленную статистику и confirmation rate;
- при критической ошибке persistence приложение переходит в `SAFE_STOP`
  и не продолжает работу на недостоверном состоянии;
- retention и cleanup удаляют завершённые циклы и старые снимки согласно
  секции `database.retention`;
- пауза между запросами к одному агрегатору задаётся общим
  `resources.provider_min_interval_seconds`, а для отдельного агрегатора —
  его собственным `min_interval_seconds`; действует то из двух
  ограничений, которое строже, и пауза одного агрегатора не задерживает
  остальных;
- лимиты `requests_per_second` и `max_concurrent_requests` применяются
  Resource Manager к очереди провайдера. Очередь одна на агрегатор, и все
  запросы к нему — BUY и SELL, Level 1 и Level 2, котировки и комиссии —
  делят общий бюджет: API ограничивает ключ целиком;
- остановка сканера командой из Telegram живёт в памяти процесса: после
  перезапуска сканирование снова разрешено;
- интервал между циклами отсчитывается **от старта** предыдущего цикла, а
  не от его завершения: старты идут по ровной сетке, и длительность
  сканирования её не сдвигает. Если цикл когда-нибудь окажется длиннее
  интервала, пропущенные слоты схлопываются в один запуск, а не
  превращаются в серию догоняющих;
- задачи планировщика выполняются параллельно и не ждут друг друга:
  идущий цикл сканирования не задерживает приём команд Telegram и
  отправку уведомлений;
- у агрегатора могут быть заданы часы работы (`schedule`): вне окна он не
  опрашивается вовсе. Это не отключение и не сбой — состояние здоровья и
  возможности провайдера расписание не меняет, а `/providers` показывает
  окно и отметку «перерыв».

## 10. Обновления операционной системы

Раз в сутки Monik проверяет список доступных обновлений и присылает его в
Telegram. Проверка выполняется на чтение и прав не требует: приложение
только читает локальный кеш менеджера пакетов. К каждой строке
добавляется короткое пояснение на русском — категория пакета и отметка
для тех пакетов, на которых работает сам сканер: их установка требует
перезапуска.

Автоматически система ставит только обновления безопасности; остальные
ждут решения оператора. Применить их можно тремя способами: вручную
командой из сообщения, командой `/update` в Telegram или кнопкой
**⬇️ Обновить и перезапустить** в самом уведомлении.

### Право на установку

Кнопка и команда выполняют установку от имени системы через `sudo -n`, то
есть **без запроса пароля**. Это осознанное расширение полномочий
приложения, и выдаётся оно вне Monik — правилом `sudo`. Пока право не
выдано, кнопка в уведомлении не появляется, а команда честно отвечает,
что права нет.

Выдавать полный беспарольный `sudo` для этого не нужно и не следует.
Достаточно разрешить ровно две команды:

```
# /etc/sudoers.d/monik-updates
monik ALL=(root) NOPASSWD: /usr/bin/apt-get update, /usr/bin/apt-get -y * upgrade
```

Файл создаётся через `visudo -f /etc/sudoers.d/monik-updates`: ошибка в
синтаксисе `sudoers` способна закрыть доступ к `sudo` целиком, а `visudo`
проверяет файл до сохранения.

Что это даёт и чего стоит:

- **даёт** — установку обновлений одним нажатием, без входа на сервер;
- **стоит** — тот, кто может отправлять команды боту, получает
  возможность запустить установку пакетов на сервере. Поэтому
  `notifications.telegram.allowed_chat_ids` должен быть задан явно:
  без него команды принимаются от любого чата, куда добавлен бот.

Установка неинтерактивна: при конфликте конфигурационных файлов
сохраняется существующий, а перезапуск затронутых служб системе не
поручается — Monik перезапускает себя сам и только после того, как ответ
оператору отправлен.

## 11. Часы работы агрегаторов

У каждого агрегатора можно задать окно, вне которого Level 1 к нему не
обращается:

```yaml
providers:
  - provider_id: velora
    schedule:
      start: "07:00"
      end: "19:00"
      timezone: "Europe/Lisbon"   # необязательно: по умолчанию application.timezone
```

Зачем: у провайдера может быть своя суточная квота, и ограничивать расход
только частотой запросов недостаточно. Двенадцатичасовое окно уменьшает
суточный расход вдвое, не трогая темп работы остальных.

Правила:

- время в формате `HH:MM`, границы трактуются как `[начало, конец)`;
- окно может пересекать полночь: `22:00 → 04:00` означает вечер и ночь;
- часовой пояс по умолчанию — пояс приложения, то есть тот же, в котором
  пишутся логи;
- провайдер без `schedule` работает круглосуточно;
- если вне окна оказались **все** агрегаторы, цикл Level 1 не
  выполняется: в журнал идёт запись `level 1 scan skipped: no provider is
  within its working hours`, пустая запись сканирования не создаётся.

Чего расписание **не** делает:

- не выключает провайдера: он остаётся настроенным, его возможности и
  состояние здоровья не меняются;
- не отражается на статистике отказов — запрос вне окна не отправляется и
  не отклоняется, он просто не возникает;
- не распространяется на Level 2: подтверждение уже найденной возможности
  идёт по зафиксированному маршруту, и отказ от него потерял бы саму
  возможность. Проверок мало, на квоту они влияют слабо;
- не распространяется на обслуживание (обновление комиссий, discovery):
  эти задачи выполняются раз в сутки.

Текущие окна видны командой `/providers`.
